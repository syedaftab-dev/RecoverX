# RecoverX — Detailed Project Description

## 1. What problem this solves

Merchants lose revenue silently, every day, in three specific moments:

- **Payment declines** — card fails, UPI times out, bank rejects. Customer wanted to buy. Money didn't move. Most merchants do nothing; customer leaves.
- **Cart abandonment** — customer adds items, hesitates, closes tab. No one follows up in the moment it matters.
- **Stock-outs mid-checkout** — item goes out of stock right as customer tries to buy. Dead end, no fallback offered.

Each moment is a **recoverable** revenue event, not a lost one — if something acts fast, explains itself, and stays within safe limits. That "something" today is usually nothing. RecoverX is that something.

## 2. What RecoverX actually is

An AI agent embedded in a merchant's checkout flow that:

1. Runs a normal conversational checkout (customer chats, agent builds cart, checks out)
2. **Watches for revenue-loss moments** in real time (decline, abandonment, stock-out)
3. **Reasons about a recovery action** — retry payment differently, offer a bounded discount, suggest an alternative product, escalate to a human
4. **Never acts outside pre-defined limits** — every discount, every retry, every dollar amount is bounded in code, not just prompted
5. **Explains every decision** in plain language, before and after acting
6. **Logs everything immutably** — a full audit trail a merchant or regulator could inspect
7. **Measures itself** — surfaces a live number: how much revenue it recovered, and at what rate

This directly answers the brief's requirement: *"grow the merchant's revenue"* + *"every money action explainable, bounded and gated"* + *"show the audit trail and one failure handled gracefully."*

## 3. Why microservices (not a single app)

This isn't infra for infra's sake — each service exists because it has a genuinely separate job and a separate trust boundary:

- **catalog-service** — owns product truth (price, stock). Nothing else should touch this data directly.
- **agent-service** — the "brain." Only service allowed to reason and decide. Everything it does must be bounded in code, because this is the one service touching an LLM, and LLMs are not trustworthy actors by default — the whole architecture exists to put a cage around this service.
- **payment-service** — the only service that talks to Razorpay. Isolating this means a bug in the agent's reasoning can never directly touch money — it can only *request* a payment action through a narrow, validated interface.
- **audit-service** — deliberately decoupled via the event bus, so logging can never be skipped, delayed, or silently dropped by a bug elsewhere. It listens; it doesn't get asked.
- **gateway (Nginx)** — single front door, and the natural place to enforce rate limits on the agent's tool-call endpoint — stopping a runaway agent loop before it even reaches the brain.

The event bus (Redis Streams) is what makes "audit trail" a structural property of the system, not a feature someone remembered to add. Every decision *must* pass through it to be considered "done."

## 4. The core trust mechanism (this is the actual differentiator)

Three-layer safety model:

1. **Bounded** — hard numeric limits live in code (e.g., discounts ≤15% auto-approve, order value ≤₹5000 auto-approve), not just in the LLM's instructions. The LLM can *propose* anything; the system only *executes* what's inside the boundary.
2. **Gated** — anything outside the bound doesn't get silently blocked or silently allowed — it pauses and asks a human. This is what makes the agent usable in a real business: it degrades to "ask permission" instead of failing open or failing closed.
3. **Explainable** — every proposed and executed action carries a plain-language reason, generated by the agent itself, stored alongside the action. Not a log line an engineer would need to interpret — a sentence a merchant could read and understand.

## 5. The recovery loop (the featured failure case)

Primary scenario for demo: **payment decline recovery.**

1. Customer's payment fails (simulated Razorpay test-mode decline)
2. Agent detects the failure event within seconds
3. Agent reasons: is this a transient failure worth retrying, or does it need a different approach (alt payment method, small friction-reducing discount within bound)?
4. Agent explains its plan to the customer in plain language, then acts within its limits — or pauses for merchant approval if the action would cross a bound
5. Outcome is logged either way: recovered or not, with the full reasoning trail
6. This becomes a live metric: **revenue recovered, recovery rate** — the single number a merchant (or judge) cares about most

## 6. What "production-grade" means for this build specifically

Not just "more technologies." Specifically:

- **Idempotency** — Redis-backed idempotency keys so a duplicate Razorpay webhook can never double-charge or double-log. This is a real production bug class, not decoration.
- **Rate limiting at the edge** — protects against a misbehaving agent loop hammering tool calls, tied directly to the "bounded" requirement.
- **Async, decoupled audit** — logging survives even if a downstream service is slow or briefly down, because it's event-driven, not a direct synchronous call.
- **Containerized, one-command boot** — `docker compose up` gets a judge (or you, mid-demo) to a working system with zero manual setup, which is itself a signal of production discipline.
- **Clear service boundaries** — someone reading the repo can see exactly which service is allowed to do what, which is the actual meaning of "bounded" applied to system design, not just to the agent's money logic.

## 7. What ships for the deadline (MVP scope, explicitly)

In scope:
- Full checkout conversation flow
- Payment decline as the one built-out failure/recovery case
- Bounded discount + bounded order value, with gating above threshold
- Full audit trail UI + recovery metric dashion
- All 6 services running via Docker Compose

Explicitly out of scope (stretch only, cut first if time runs short):
- Cart abandonment recovery
- Stock-out recovery
- Load balancer replicas (nice mention, not core to the story)
- Any second LLM/model comparison work
